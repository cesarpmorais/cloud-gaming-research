# Paper Analysis: Congestion Control for Cloud Gaming Over UDP Based on Round-Trip Video Latency (C³G)
**Alós, Morán, Carballeira, Berjón, García — IEEE Access, 2019**

**The most directly relevant prior work for our TCC.** Server-side,
RTT-based, UDP-native congestion control for cloud gaming, built on
PlayGiga and inspired by Google's BBR. Same problem statement, same
operating constraints, almost the same signal. We need to be honest about
this: the "server-side, RTT-based ABR for cloud gaming" framing is **not
novel** — Alos2019 already did it. What is novel for our TCC narrows
sharply (see Section 7).

---

## 1. Problem Framing

Cloud gaming (CG) over UDP with strict requirements:
- **No packet losses** (video frames are not retransmittable in time).
- **Round-trip end-to-end latency below 100 ms** for action games
  (their `RTVL_th`).
- **Maximize channel utilization** without crossing into bufferbloat.

They define the *Round-Trip Video Latency (RTVL)*: per-frame round-trip
delay measured **at the server**, from when the raw frame is handed to
the encoder (`S₀`) until the client's frame-ACK arrives (`S_ACK`). RTVL
includes encoding delay + downlink transmission + decoding delay +
uplink ACK delay. This is the application-layer analog of BBR's
TCP-level RTT — but **per video frame**, not per packet, and **at the
application layer**, which is what makes it implementable over UDP.

Their explicit positioning: BBR uses TCP's RTT, which is "too late to
react" because the symptom (RTT inflation) shows up well after the buffer
has started filling. RTVL is a strictly better predictor for CG because
it bundles all the delays that actually matter to QoE.

---

## 2. Input Signals

All server-observable; the client sends regular keep-alive packets that
report the receive rate `μ(t)`.

### Per-frame RTVL
- Server timestamps `S₀` when raw frame goes to the encoder.
- All UDP packets of the encoded frame are sent.
- Client reassembles, decodes, displays — and sends a single frame-ACK
  over UDP.
- Server timestamps `S_ACK` on ACK arrival.
- `RTVL = S_ACK − S₀`.

This is **much richer than ENet's peer-RTT** that our TCC uses, because
it captures the full media path (including the encoder and decoder
queueing). It is also more expensive: it requires the *client* to send
a per-frame ACK, which Moonlight does not do.

### Server-sent and client-received rates
- `λ(t)` — bytes sent by server in a window. Measured at server.
- `μ(t)` — bytes received by client in the same window. Reported via
  TCP-KeepAlive-style packets (which they piggy-back on for free).
- `qdData(t) = ∫(λ−μ)dt` — accumulated queued data in the bottleneck.
  When `qdData > 0` and `RTVL` is rising, congestion is declared.

### Packet loss fraction `l(t)`
- Computed at the client, reported per frame. Used in their
  generalization of the `λ_drain` equation to account for retransmissions.

## 3. Congestion Model (3 phases)

```
t < t₀     [sub-OOP]      : λ < c_btl, qdData=0, RTVL = RTVL_min
                            (channel underused — proactive exploration
                             should try higher λ)

t₀ ≤ t ≤ t₁ [congestion]  : λ > c_btl, qdData growing, RTVL rising
                            (still time to react before saturation)

t > t₁      [bufferbloat] : buffer full, packets dropped, RTVL = RTVL_max
                            (must be avoided)
```

The control objective is to spend as much time as possible at the
**Optimal Operating Point (OOP)** — top of phase 1 / bottom of phase 2,
where the bottleneck is saturated but the buffer is empty. Reach it
reactively from above (when capacity drops) and proactively from below
(when capacity rises).

This 3-phase model is borrowed from BBR/Kleinrock but applied at the
application layer over UDP for the first time.

---

## 4. Algorithm

C³G has two halves, both running periodically with period `Δt`.

### A. Reactive bitrate decrease (when congestion is detected)

Detection (Equation 1):
```
congestion(t_now) = (qdData(t_now) > 0) AND (RTVL_avg(t_now) > RTVL_avg(t_prev))
```
i.e., buffer non-empty AND latency trending up. (In implementation,
`qdData > 0` is replaced with `λ̄ − μ̄ > ε` to filter window misalignment
noise.)

Once detected, predict two RTVL trajectories one step ahead:
1. `RTVL₁(t_next)` — linear extrapolation from recent RTVL samples.
2. `RTVL₂(t_next)` — what RTVL would become if `qdData` keeps growing
   at rate `μ̄` (the current bottleneck estimate).

If **either** prediction exceeds `RTVL_th = 100 ms`, declare
`drainNeeded` and launch the drain sequence:

```
λ_drain   = μ̄(t_drain) − qdData(t_drain) / Δt    (equation 2)
T_drain   = qdData(t_drain) / (μ̄(t_drain) − v_min)
λ_OOP     = μ̄(t_drain)
```

Hold the server-sent rate at `λ_drain` for `T_drain`, then jump up to
`λ_OOP`. This is more sophisticated than ABRAGame's flat `estBW − margin`
because it accounts for *how much buffer needs to drain*, not just
where to land afterward.

When packet loss `r(t)` exists, the drain rate is corrected:
`λ_drain = (1 − r) · μ̄ − qdData/Δt`.

### B. Proactive bitrate increase (exploration)

This is the part that goes beyond AIMD. Instead of a fixed step,
C³G maintains a **network state dictionary** `S = {s(λ̄)}` where each
entry pairs a recently-explored bitrate `λ̄` with a *rating* `R(λ̄)`:

```
R(λ̄) = [a·RTVL_avg + b·σ(RTVL) + c·max(RTVL) + d·qdData] / λ̄    (eq. 3)
```

with `(a, b, c, d) = (1, 10, 1, 2)` in their tests. Lower `R` = better
network behavior at that bitrate.

Each exploration period, choose between three candidate next-rates:
`λ₊ = λ̄ + λ_exp`, `λ₌ = λ̄`, `λ₋ = λ̄ − λ_exp`. Pick the one with the
best historical rating, breaking ties toward exploration (going up).

The exploration step `λ_exp(t) = g(t) · λ_exp,min` and period
`T_exp(t) = (g_max − g(t) + 1) · Δt` are *jointly* modulated by an
exploration gain `g(t) ∈ [1, g_max=50]`. When the previous exploration
period went well, `g` increases — step grows, period shortens →
"exponentialish" probing. When it went badly, `g` decreases —
shorter, more cautious steps. This is essentially a learned-from-history
substitute for BBR's fixed `×1.25 / ×0.75` gain cycle.

## 5. Evaluation Methodology

### Testbed
- **PlayGiga** real CG platform.
- Server: AMD Radeon RX 480 GPU, AVC/H.264 encoder at 720p30 with
  peak-constrained bitrate (acting on QP).
- Client: Intel i7-6500U / Intel HD 520 GPU.
- Network: real WAN, **9 hops, ~30 km**.
- Bottleneck shaping via Linux TBF (Token Bucket Filter) on a
  separate node, 100 ms typical queuing delay.
- Game: *Sonic & All-Stars Racing Transformed* — chosen for high-frequency
  textures + fast motion (stresses the encoder).

### Scenarios
- 60 combinations of `(c_btl,lim, α_c)`:
  - `c_btl,lim ∈ {5, 7, 9}` Mb/s
  - `α_c ∈ {1.25, 1.5, 1.75, 2, 2.5}` (capacity drop ratio from
    `c_btl,init = α_c · c_btl,lim`)
- Each (capacity, drop ratio) combination tested 4 times.
- Two phases per test: reactive (drop) + proactive (recovery to
  initial capacity, "EP" = Exploration Period).

### Baselines
- **BBR re-implemented for UDP at the application layer** (using
  `RTVL` instead of TCP RTT, `μ̄` for `BtlBW`, etc.). They re-implemented
  BBR following ns-3 [16, 30] guidelines and adapted it for the
  application layer.
- They explicitly note that BBR is the closest algorithmic prior art
  for this CG-over-UDP setting.

### Metrics
- **AP** (Adaptation Period): time after capacity drop during which
  `RTVL` exceeds the 100 ms playability threshold.
- **RTVL_peak**: maximum `RTVL` during AP.
- **L_AP**: number of lossy frames during AP.
- **Effective channel use** `λ̄/c_btl` (%).
- **L_rate**: lossy frames per second.
- **R_rate**: retransmitted data rate (kb/s).
- **EP** (Exploration Period): time to recover `λ ≈ c_btl,init` after
  capacity restoration.

---

## 6. Key Results

### Reactive performance (capacity drop)
- **AP: C³G 0.4–0.8 s vs BBR >1 s** (often 2+ s for higher `α_c`).
- **RTVL_peak: both reach ~350 ms** at saturation (`α_c > 1.75`); below
  that, C³G keeps RTVL well below 100 ms while BBR overshoots.
- **L_AP: C³G ≈ 0 lossy frames for `α_c < 1.75`, ≤ 10 always**;
  BBR exceeds 10 lossy frames for moderate `α_c`, reaches 20+ frequently.
- **Below ~42% capacity drop (`α_c < 1.75`), C³G is loss-free** —
  this is the headline number the abstract advertises.

### Stable channel performance
- **Effective channel use: C³G 93.2–96.1% vs BBR 86.9–93.4%**
  (2.7–6.3 percentage points better).
- **RTVL_avg: C³G ~37–40 ms vs BBR ~42–46 ms.**
- **L_rate: ≈ 0 fps for both** in the stable window.

### Exploration period (capacity recovery)
- **EP: C³G 36.2 ± 16.4 s vs BBR 8.3 ± 8.6 s.**
- BBR is faster to recover because it uses fixed ×1.25 gain cycles.
  C³G is slower but prioritizes "minimal losses followed by low
  latency over fast bitrate increase" — explicit design tradeoff.
  In their view, BBR's faster recovery is its **only** advantage and
  it doesn't compensate for the AP / RTVL / loss penalty during drops.

### Resilience bound
- **Channel capacity drops up to ~42% are absorbed with zero packet
  losses** (`α_c < 1.75`).
- Above that, even C³G incurs losses but still beats BBR on every
  metric.

## 7. Implications for Our TCC — What Changes

### What this paper means for our positioning

Alos2019 **already implemented** the algorithm we are describing as our
contribution:
- Server-side: ✓
- RTT-based: ✓ (theirs is RTVL, ours is ENet `peer->roundTripTime`)
- No client modification needed: ✓ (mostly — see below)
- UDP-native: ✓
- Cloud-gaming specific: ✓
- Evaluated on real CG platform with shaped WAN: ✓

So the framing *"a server-side RTT-based adaptive bitrate controller for
cloud gaming"* is no longer novel. We need to sharpen the contribution.

### Where our TCC is genuinely distinct

| Dimension | C³G (Alos 2019) | Our TCC |
|---|---|---|
| Platform | PlayGiga (proprietary, closed-source) | **Sunshine (open-source)** |
| Encoder | Software AVC/H.264, QP-constrained | **NVENC hardware via FFmpeg avcodec on Linux** |
| RTT statistic | Per-frame RTVL (requires client frame-ACK) | **ENet `peer->roundTripTime` (already maintained)** |
| Client cooperation | Requires per-frame ACKs from CG client | **None — Moonlight unmodified** |
| Policy | Reactive drain + proactive exploration with state dictionary | **Plain AIMD (simpler)** |
| Comparison baseline | BBR-on-UDP (re-implementation) | **Fixed-bitrate Sunshine** |
| Reproducibility | Cannot rerun their tests | **Fully reproducible** |

The **genuine novelty narrows to**:
1. **Open-source instantiation** — anyone can rerun this. Alos2019 is
   forever frozen behind PlayGiga.
2. **No client modification** — even C³G needs the CG client to send
   frame-ACKs. We use a signal (ENet RTT) that the client already maintains
   for an unrelated reason. This is a stronger "no client cooperation"
   property than the paper claims.
3. **Hardware-encoder pipeline** — the modern reality (NVENC, VAAPI,
   AMF) was not in scope for them. We hit the avcodec-rebuild issue that
   software libx264 / QP-knob encoders do not have.
4. **Simpler policy** — AIMD vs reactive-drain+state-dictionary. Our
   thesis question shifts to: *"how much of C³G's complexity is
   actually needed for cloud-gaming-over-Sunshine, given that we use a
   coarser signal?"* That's a legitimate research question.

### What we should outright borrow

- **`RTVL_th = 100 ms`** as our playability threshold for the metric
  "time spent in degraded state." This is a peer-reviewed number from a
  CG-specific paper — much better than the generic "70 ms RTT" we have
  been citing via Baldovino.
- **The AP / RTVL_peak / L_AP metric triple.** These are the exact
  three numbers the field measures for reactive performance. Our
  scenario A (abrupt drop + rapid recovery) should report all three.
- **The `α_c < 1.75` (≈42% drop) "loss-free zone"** as a comparison
  bound. If our AIMD controller absorbs 42% drops loss-free, we match
  C³G; if not, we have a clear baseline to compare against.
- **Effective channel use `λ̄/c_btl`** as a stable-window metric.
  C³G hits 93–96%; this gives us a quantitative target.
- **The 60-test grid `c_btl,lim × α_c`.** Their `(5, 7, 9) × (1.25, 1.5,
  1.75, 2, 2.5)` design directly maps onto a useful sub-grid of our 7
  scenarios. Worth adopting partially.

### What we should NOT replicate

- **Per-frame frame-ACKs from the client.** Out of scope (no Moonlight
  changes). Use ENet RTT instead and accept the coarser cadence.
- **Network state dictionary with rating function `R(λ̄)`.** Too complex
  for the 2-month TCC scope. Our AIMD is a deliberately simpler
  alternative — and a clean research question is whether the simpler
  policy is enough.
- **Re-implementing BBR for comparison.** Our baseline is fixed-bitrate
  Sunshine. C³G already published BBR-on-UDP numbers; if we want a
  BBR comparison, we cite C³G's results rather than re-running them.

## 8. Algorithmic Comparison Across All Surveyed Papers

| Paper | Where signal is computed | What signal | Action policy | Cadence |
|---|---|---|---|---|
| GCC (2016) | Receiver | One-way delay gradient (Kalman) | α=0.85 / η=1.05 multiplicative | Per frame (~30 Hz) |
| Hong (2015) | Client (WBest dispersion) | Measured bandwidth | MOS-maximizing (f, b) selection | ~seconds |
| ABRAGame (2025) | Client | Cumulative one-way latency / 500 ms | `estBW − 1.5 Mbps` decrease, `+0.5 Mbps` / 20 s increase | 20 ms sampling |
| **C³G (2019)** | **Server** | **Per-frame RTVL + qdData** | **Reactive drain + proactive state-dict exploration** | **Per Δt control loop** |
| **Our TCC** | **Server** | **ENet peer RTT inflation** | **AIMD (BETA=0.7, +STEP / STABLE_TIME)** | **~1 s window** |

C³G is the row closest to ours. We sit between C³G and ABRAGame in
signal richness (coarser than RTVL, no clock sync) and far simpler than
both in policy.

## 9. Acknowledged and Implicit Limitations

### Acknowledged by Alos et al.
- λ(t) and μ(t) time windows are misaligned (uplink + downlink
  propagation), introducing noise into `qdData` estimation. Mitigated
  with a threshold `ε > 0` but never fully resolved.
- Setting `λ(t)` does not directly set the encoder's `v(t)` — there's a
  proprietary translation layer (NVIDIA/Intel/AMD encoder APIs) that they
  describe as a "black box." They cope by tracking the historical
  `λ/v` ratio.
- `RTVL_max` (~350 ms in their tests) is a function of the buffer size +
  presentation timeout (100 ms) — system-specific, not portable.
- 50 fps tests showed measurable frame-loss rate even at moderate CRF —
  same kind of finding as Hong2015's Table II.

### Implicit
- **Closed-source platform** (PlayGiga) → not reproducible.
- Single game tested (*Sonic Racing*); generalization not validated.
- Software encoder (QP-knob); modern hardware-encoder reality not in scope.
- Per-frame ACKs add uplink traffic (small but nonzero), and require
  client cooperation.
- No QoE / MOS study; all metrics are objective QoS.

## 10. Directly Reusable Elements for Sunshine TCC

| Element | How we adapt it |
|---|---|
| `RTVL_th = 100 ms` playability threshold | Adopt directly as our "degraded state" threshold; supersedes the generic 70 ms via Baldovino for action-game framing |
| AP / RTVL_peak / L_AP reactive metrics | Compute these for each scenario; AP = time RTT > threshold after a drop |
| Effective channel use `λ̄ / c_btl` | Stable-window metric; target ≥ 90% with fixed bitrate and adaptive controller alike |
| 42% loss-free drop bound | Compare our controller against C³G's claimed bound for scenario E |
| `(c_btl,lim, α_c)` test grid concept | Inspire the bandwidth × drop-ratio sub-grid in our scenarios |
| Reactive drain with `T_drain` | If our flat AIMD decrease is too slow, the next iteration could compute a drain period explicitly (their Equation 2) |
| State-dictionary exploration | Listed as "future work" in TCC; out of scope for the 2-month timeline |

### Key Insight

**Alos2019 is the paper our TCC should be *compared to*, not the paper
our TCC duplicates.** They built the sophisticated server-side
RTT-based controller for CG on a proprietary platform; we are building
the **simplest possible server-side RTT-based controller on
Sunshine**, evaluating whether the simpler policy is good enough, and
documenting the open-source implementation so anyone can extend it
toward a C³G-class controller.

The TCC narrative should explicitly frame our work as:

> *"Alos et al. demonstrated on the proprietary PlayGiga platform that a
> server-side, RTT-driven adaptive bitrate controller can keep cloud
> gaming latency below 100 ms and avoid packet losses for capacity
> drops up to ~42%. Their algorithm requires per-frame client ACKs and
> a learned network state dictionary. We ask whether the same outcome
> is achievable on the open-source Sunshine platform with (i) no client
> modification and (ii) a plain AIMD policy driven by ENet's existing
> round-trip time measurement. If yes, the result is a fully
> reproducible deployment-ready baseline for the cloud-gaming ABR
> design space."*

Alós et al. (2019) (**C³G**) is the closest prior work to our TCC. They already published:

* Server-side congestion control for cloud gaming
* Round-trip latency as the primary signal (their RTVL = our RTT inflation in spirit)

* BBR-inspired algorithm adapted for cloud gaming

The framing **"server-side, RTT-based adaptive bitrate controller for cloud gaming"** is not novel anymore. We have to be honest about this in the TCC.
