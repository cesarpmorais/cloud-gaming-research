# Paper Analysis: Enabling Adaptive Cloud Gaming in an Open-Source Cloud Gaming Platform
**Hong, Hsu, Tsai, Huang, Chen, Hsu — IEEE TCSVT, 2015**

The direct ancestor of what we are doing in PR #2a. They extend
**GamingAnywhere (GA)** — the 2014 open-source cloud gaming platform —
with runtime codec reconfiguration and multi-gamer bitrate allocation.
Sunshine is the modern equivalent of GA; our PR #2a is the modern
equivalent of their codec reconfiguration work. **This is the closest
implementation-level prior art we have.**

---

## 1. Problem Framing

Hong et al. tackle three coupled problems for open-source cloud gaming:

1. **Quantify gamer experience** under different bitrate/framerate settings
   via a crowdsourced MOS study (since lab studies don't scale).
2. **Reconfigure the video codec on-the-fly** — GA at the time only supported
   static codec parameters; once a session started, frame rate and bitrate
   could not be changed. They fix this in code.
3. **Allocate bandwidth across concurrent gamers** sharing a datacenter
   uplink, optimizing either average MOS or worst-case MOS.

Our TCC overlaps with (2) directly and with (1) loosely. Problem (3) is
multi-tenant resource allocation and is out of scope for our single-gamer
home-streaming setup.

## 2. Input Signals

### Effective bandwidth estimation
Inspired by **WBest**. Key observation: a 30 fps video frame is much
larger than the path MSS, so each frame is split into multiple back-to-back
packets. The **dispersion time** between those packets gives a sample of
the bottleneck's instantaneous capacity, without injecting any probing
traffic.

- Take median dispersion across `W` packets to estimate capacity.
- Send `W` video packets at the estimated capacity to measure effective
  bandwidth (capacity minus competing-traffic share).
- `W = 200` chosen empirically: 80%+ accuracy, reasonable reaction time.
- Estimator runs at the **GA client** and reports back to the server.

Smoothed with EWMA before being fed to the codec parameter selector.

### MOS model (the signal that decides the action)
Per-game quadratic regression on `(fps, bitrate)`:

```
m(g, f, b) = α_{g,1}·f + α_{g,2}·b + α_{g,3}·f² + α_{g,4}·b² + α_{g,5}·f·b + α_{g,6}
```

Coefficients fitted from the crowdsourced study (Section IV). R² ≈ 0.97–0.99
across the three test games. MOS saturates around ~2 Mbps for all three
games tested.

### Not used
- RTT / one-way latency (explicitly excluded: "network latency is not
  controllable by the GA server/client during ongoing sessions")
- Loss rate
- Packet jitter
- Server-side queue depth

## 3. Algorithm / Approach

### Codec reconfiguration mechanism (Section V — directly relevant)

This is the part that matches our PR #2a almost line-for-line.

**Migration ffmpeg → live555.** They couldn't reconfigure the encoder
inside ffmpeg's tightly-coupled RTSP+RTP+codec stack, so they replaced the
RTSP stack with live555 and added an **`ioctl` interface** between the
RTSP server and the codec modules. This decoupling — *separate the streaming
session from the encoder lifecycle* — is exactly the pattern we land on
with `MAIL(bitrate_change)` events + per-frame `apply_pending_bitrate()`.

**libx264 (software) reconfiguration.** They could not use ABR mode because
*"the bitrate cannot be changed once the encoder is initialized"* — the
same fundamental limit our PR #2a hit on Linux NVENC via ffmpeg avcodec.
Their workaround: use CRF/CQP modes with `vbv-maxrate` and `vbv-bufsize`
caps, reconfigured via `x264_encoder_reconfig`. They warn that mismatching
`crf` and `vbv-maxrate` causes "mosaic blocks" on partially-encoded frames
— a useful failure mode to remember if our reconfigured frames ever look
broken under load.

**VPU (Freescale i.MX6) and QSV (Intel) hardware paths.** Both supported
runtime bitrate, framerate, GOP, and slice mode changes. **QSV had to
reset the encoder** for some parameters but not for target bitrate. This
2015-era split between "soft reconfigure" and "hard reconfigure" is exactly
what motivates our `nvEncReconfigureEncoder()`-vs-AVCodecContext-rebuild
discussion in [[encoders]].

**Measured framerate loss rate** (their Table II) is non-zero only at 50
fps under aggressive CRF settings — at 24/30 fps with reasonable CRF, 0%
frames are dropped during reconfiguration. This is empirical justification
for our PR #2a finding that runtime reconfiguration **does not cause
broadcast stalls** in practice.

### Codec parameter selector

Given the current effective bandwidth `R`, the selector picks `(f, b)`
to maximize MOS subject to `b ≤ R`. For a single gamer this is just
"hill-climb the MOS contour from Figure 14 along the bandwidth constraint."

For multiple gamers (Section VI), they reduce the problem to allocating
residual bandwidth incrementally:
- **EFF_avg**: at each step, give an extra `w` kbps to the gamer with the
  highest MOS-improvement slope `c_u`. Maximizes mean MOS.
- **EFF_mm**: at each step, give the extra `w` kbps to the gamer with the
  **lowest** current MOS. Maximizes minimum MOS (fairness).

Both shown to match the optimal CPLEX solution in polynomial time. Up to
46% improvement over equal-share baselines, scales to 8000 gamers in
~1.7 s.

## 4. Evaluation Methodology

### Crowdsourced MOS study
- 101 subjects, 167 experiments, **3020 game sessions**, 132 h total
- Games: Lego Batman (3D adventure), Sin Cyber Grandprix 2 (racing),
  Call of Duty: MW2 (FPS) — chosen for genre coverage
- Configurations: bitrate ∈ {0.5, 1, 2 Mbps} × fps ∈ {10, 20, 30}
- MOS on a **1–7 scale** (not the usual 1–5), justified by needing finer
  resolution between adjacent video qualities
- Each subject plays all 9 configurations of one game; order randomized;
  MAC-keyed forms to filter spam
- Three sub-scores: graphics quality, interactivity, overall

### Codec reconfiguration testbed
- One GA server + one GA client over a Dummynet bridge
- Cycled bandwidth among {2048, 1024, 512} kbps every 60 s
- Measured: bandwidth-estimator response, effective on-the-wire
  bitrate, frame rate trajectory

### Multi-gamer simulator
- Java simulator, MOS model from study, EC2-measured datacenter
  bandwidth traces (760 Mbps, 96 samples over 1 day)
- `U ∈ {250, 500, 1000, 2000, 4000, 8000}` gamers
- Baselines: equal-allocation, MOS-proportional allocation

### Metrics
- Mean / worst MOS across gamers
- Per-gamer allocated bitrate
- **Efficiency** = MOS / Mbps (a QoE-per-bit ratio worth borrowing)
- Algorithm running time
- Link utilization (across gamers and at the data center)

## 5. Key Results

### MOS findings (the ones worth quoting)
- **Higher framerate hurts at low bitrate.** At 0.5 Mbps, going from 10 to
  30 fps *lowers* overall MOS — there are not enough bits per frame to keep
  quality acceptable.
- **Higher framerate helps at high bitrate.** At 2 Mbps, 30 fps is best.
- Therefore the right action under bandwidth constriction is not "drop fps
  to keep bitrate" or "drop bitrate to keep fps" — it's **both axes
  jointly**, chosen from the MOS contour.
- MOS saturates around **2 Mbps** for the three games tested at 720p — i.e.,
  beyond ~2 Mbps you're spending bandwidth for marginal QoE.
- Higher screen resolutions and larger physical displays *amplify*
  imperfections → users score lower MOS for the same encoded stream.

### Codec reconfiguration empirical results
- Bandwidth estimator successfully tracked Dummynet's induced 2 → 1 → 0.5
  Mbps switches within seconds.
- Codec parameter selector "quickly recovered from sudden frame rate drops
  due to throttled bandwidth, by adjusting the video coding parameters
  (bitrate and frame rate)."
- 0% frame loss under software reconfiguration at 24/30 fps (Table II).

### Multi-gamer
- EFF_avg vs equal-share: up to **30%** mean-MOS improvement.
- EFF_mm vs equal-share: up to **46%** worst-MOS improvement.
- Polynomial time, scales to 8000 gamers in ~1.7 s.

## 6. Game Streaming Specifics — What Transfers and What Does Not

### What transfers cleanly to our TCC

- **The MOS-saturates-around-2-Mbps finding.** Direct quantitative
  justification for our `MIN_BITRATE = 1 Mbps` / `MAX_BITRATE ≈ 19 Mbps`
  clamp — well above their saturation point, so we are operating in the
  diminishing-returns region. If we ever want to argue *why* a controller's
  unnecessary drop from 19 → 8 Mbps is not catastrophic for QoE, Figure 5
  of this paper is the citation.
- **Framerate-aware QoE.** Reminds us that "lower bitrate" is not the only
  knob. ABRAGame and our PR #2a only adjust bitrate; Hong2015 adjusts
  *both* bitrate and framerate. If our scenario E baseline survives but
  with degraded image, a future PR could add framerate adaptation alongside
  bitrate — directly extending Hong2015 with modern Sunshine.
- **Architectural pattern: decouple session-level RTSP from
  encoder-level reconfiguration via an ioctl/event channel.** This is what
  our `MAIL(bitrate_change)` + `apply_pending_bitrate()` already implements.
  We landed on the same pattern independently — useful validation.
- **Codec-reconfig hard-vs-soft distinction.** Their VPU vs QSV split
  (some params hot-reconfigure, others require reset) mirrors our Linux
  avcodec vs Windows NVENC SDK split. Worth citing as evidence that this
  is a recurring architectural pattern in cloud-gaming codec layers, not
  a Sunshine quirk.
- **Crowdsourced MOS methodology.** If our blind-MOS protocol ever scales
  beyond 5–10 sessions, this paper is the template: 1–7 scale,
  per-(bitrate, fps) ratings, three sub-scores (graphics, interactivity,
  overall). Their finding that **interactivity** correlates strongly with
  framerate while **graphics quality** correlates with bitrate could
  inform how we describe degradation in our 7 scenarios.
- **`efficiency = MOS / Mbps` as a metric.** Worth borrowing alongside
  GCC's channel utilization. Gives a single scalar that captures
  "controller is delivering QoE *per bit it spends*" — a clean way to
  compare fixed vs adaptive when both achieve playability but at different
  bitrates.

### What does not transfer

- **Client-side bandwidth estimation via packet dispersion.** Two problems:
  (i) Sunshine cannot modify Moonlight; (ii) the dispersion method assumes
  the receiver clocks packet arrivals from the same flow, which is
  difficult to retrofit. We replace it with server-side RTT inflation.
- **Multi-gamer resource allocation.** Hong2015's central contribution is
  EFF_avg/EFF_mm across a datacenter uplink. Sunshine is single-tenant by
  design — one user, one home connection — so this entire problem class
  goes away.
- **MOS-driven action.** They use the MOS model itself as the optimization
  objective; our controller is a delay-driven AIMD that does not know about
  MOS at all. The MOS model is useful for *post-hoc* evaluation, not
  online decision-making in our design.
- **Quadratic MOS coefficients.** Fitted to libx264 at 720p in 2014. Our
  hardware encoders (NVENC H.264/HEVC/AV1) and modern 1080p+ Moonlight
  produce different MOS surfaces. Their methodology is reusable; their
  numbers are not.
- **ffmpeg→live555 migration.** Sunshine does not have GA's ffmpeg-RTSP
  coupling problem. The lesson generalizes, the engineering does not.

### One concrete improvement we should consider

Hong2015 reports that **mismatched `crf` and `vbv-maxrate` cause
mosaic-block artifacts on partially-encoded frames**. We should check
whether our avcodec rebuild path on Linux honors `vbv-bufsize` correctly
after the rebuild — if not, scenario E with rapid step-downs could exhibit
this artifact and we'd misread it as a generic "bad image at low bitrate"
when it's actually a reconfiguration glitch. Worth adding to the PR #2b
QA checklist.

## 7. Acknowledged and Implicit Limitations

### Acknowledged
- MOS model ignores network latency ("not controllable by GA")
- 3 games only; generalizing to other genres requires more crowdsourcing
- Display setting effects (resolution, pixel density) noted but not modeled
- libx264 ABR mode unusable for runtime reconfig at the time — a tooling
  limitation, not a fundamental one

### Implicit
- All evaluation is at 720p; 1080p+/HDR not considered
- No comparison against a *delay-based* controller (GCC predates this paper)
- Bandwidth estimator measured against Dummynet, not real Wi-Fi /
  cellular paths
- Single-bottleneck assumption (datacenter uplink); modern home streaming
  has the bottleneck on the residential uplink

## 8. Directly Reusable Elements for Sunshine TCC

| Element | How we adapt it |
|---|---|
| Decouple RTSP session lifecycle from codec lifecycle | Already done via `MAIL(bitrate_change)` + per-frame drain |
| Soft vs hard codec reconfigure | Already mapped: Linux avcodec = hard rebuild + IDR; Windows NVENC SDK = soft via `nvEncReconfigureEncoder()` |
| 2 Mbps MOS saturation point | Cite as justification that our 1–19 Mbps range is well above the saturation cliff |
| Crowdsourced MOS protocol | If we scale blind-MOS, adopt 1–7 scale + 3 sub-scores (graphics / interactivity / overall) |
| Efficiency = MOS / Mbps | Add as a derived metric in our evaluation |
| Joint (fps, bitrate) adaptation | Out of scope for our TCC but is the natural next step for a follow-on PR |
| Avoid mismatched VBV params on reconfig | Add a QA check that rebuilt AVCodecContext has consistent `bit_rate` / `rc_buffer_size` |

### Key Insight

**Hong2015 is the "yes, we have implemented runtime codec reconfiguration in
an open-source cloud gaming platform before" reference.** Our TCC re-does
this work for the modern stack (Sunshine instead of GA, NVENC instead of
libx264, ENet RTT instead of WBest dispersion, AIMD instead of MOS
maximization). The contribution is not "first to do this" — it is "first
to do this **server-side with no client modification, using only
server-observable signals, on a modern hardware-encoder pipeline.**"

We should explicitly cite Hong2015 as the prior implementation in the TCC
literature review, and frame our PR #2a not as a novel mechanism but as
"the Hong2015 mechanism, ported to Sunshine + NVENC + avcodec, with a
different signal."
